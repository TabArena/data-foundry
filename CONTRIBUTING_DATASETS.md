# Contributing a Dataset to Data Foundry

A dataset in Data Foundry is a folder with one `dataset.py`: a class that turns the raw download into a curated
container (data, task, outer splits, metadata) the same way on every run. This guide goes from an accepted candidate
to a merged definition. For a first contribution to TabArena v0.2, start with the
[getting-started guide](datasets/_dev/tabarena-v0pt2/GETTING_STARTED.md).

> [!NOTE]
> The BeyondArena datasets were built with Data Foundry v1 (curation notebooks). v1 is retired for new datasets;
> what is left of it is in [DATA_FOUNDRY_V1.md](DATA_FOUNDRY_V1.md).

---

## 1. Where a dataset lives

```
datasets/_dev/tabarena-v0pt2/<unique_name>/
├── dataset.py      # the definition: the only file edited by hand
├── explore.ipynb   # the workbench: `ds = workbench()` picks up every edit to dataset.py
└── README.md       # generated by `dataset check` / `dataset build`: the evidence, never edited by hand
```

The raw files go to `local-data-warehouse/<unique_name>/` (gitignored; `$DATA_FOUNDRY_WAREHOUSE` overrides it), and
`dataset build` saves the container next to them. [`datasets/README.md`](datasets/README.md) explains the rest of the
tree.

Every dataset starts as a curation record, [`curation/records/<unique_name>.md`](curation/records), whose verdict is
`Yes`; the record's comments carry the decisions the definition implements (target, split, caveats).

## 2. The steps

All commands run from the repository root in the repository's environment (`.venv/bin/python`).

1. **Scaffold the folder.** `.venv/bin/python -m data_foundry.curation.cli dataset new <unique_name> --root
   datasets/_dev/tabarena-v0pt2` copies [`datasets/_template/`](datasets/_template/). In Claude Code,
   `/add-dataset <unique_name>` does this from the record and pre-fills the metadata.
2. **Get the raw data** into `local-data-warehouse/<unique_name>/`, and write the commands that did it into
   `download_description`.
3. **Fill in `dataset.py`.** The metadata attributes (year, domain, source, license, BibTeX, curation comments), the
   task (`target`, `problem_type`), the regime (`grouping = Grouping(...)` for a grouped task,
   `temporal = Temporal(...)` for a temporal one, neither for IID), and the hooks: `_load_raw` only reads,
   `_clean` drops and fixes, `_feature_types` names the categorical, string and datetime columns. Resolve every
   `TODO(verify)`.
4. **Look at the data** in `explore.ipynb`.
5. **Check.** `.venv/bin/python -m data_foundry.curation.cli dataset check <folder>` runs the whole pipeline and the
   bundle checks without saving, and writes `README.md`. Repeat until there are no errors. A warning that is correct
   for the dataset goes into `accepted_check_warnings = {"<slug>": "<why>"}`; the reason is the audit trail.
6. **Probe.** `.claude/skills/verify-dataset/scripts/leak_probes.py <unique_name>` (leaks), `task_probes.py`
   (signal against dummy baselines) and, for a grouped task, `group_probes.py`.
7. **Second opinion.** `/verify-dataset <unique_name>` in Claude Code: the provenance, scope, split and leakage
   judgment the checks cannot make. Its `cannot-verify` items are what a reviewer reads first.
8. **Open a PR** with `dataset.py`, `explore.ipynb` and the generated `README.md`. After review a curator runs
   `dataset build`, which saves the container with a new UUID and records it in the README; the working copy's
   `CHANGELOG.md` and dataset table are updated in the same change.

## 3. What the base class does

[`AbstractCuratedDataset`](src/data_foundry/v2/dataset.py) holds the conventions, so a definition does not repeat
them: the dtype casts from `_feature_types`, the row order (a shuffle with seed 42, or a stable sort by the time
column), the split protocol (3 folds, or at least 3 temporal windows; at most 1M train and 500k test rows per split;
larger data as a sub-sampled `<name>_1m` version), standard NaNs, the metadata validation, the bundle checks and the
verification of the saved container. Recipes for the recurring cases (every split regime, sub-sampling, leaks,
dtypes, accepted warnings) are in [`dataset_patterns.md`](.claude/skills/add-dataset/references/dataset_patterns.md).

## 4. Practices

* **Reproducible downloads.** `download_description` is a human-runnable script; pin URLs to permanent locations
  (DOI, archived release) rather than mutable links.
* **Honest comments.** `curation_comments` records what was dropped and why, anomalies left in on purpose
  (`Anomaly:`, `Note:`), and sampling choices. Someone re-curating the data in two years reads it first.
* **One task per container.** Two reasonable targets or two split regimes are two datasets with their own
  `unique_name`.
* **Versions.** A derived version (for example sub-sampled) sets `version_of` and `version_comment`.
* **Same result everywhere.** Sort with `kind="stable"`, sort file listings, seed every random step; the
  definition check refuses the common nondeterministic calls.
* **Raw data stays out of git.** Only the definition folder lands in the PR.
