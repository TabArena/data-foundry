## In brief

**Question.** How long will each of 11 configurations of the solver clasp take on a logic-programming problem of a kind not seen before?

**Use case.** Algorithm selection: a user of answer set programming (a way to state and solve search problems in logic) predicts the runtime of each configuration on a new problem instance and runs the one predicted fastest, as the selector claspfolio 2 does (ASlib, Bischl et al. 2016); here for a kind of problem not seen before.

**One row.** One run of one of 11 clasp configurations on one instance of the Potassco benchmark set, stopped at 600 seconds (1,212 instances from 75 problem families that at least one configuration solved, 13,332 runs; ASlib, 2014).

**Predicted.** The run's time in seconds, on a log scale; a run stopped at the 600-second limit counts as 600 (1,963 runs, on 38% of the instances).

**Known at prediction time.** The configuration's name, statistics of the instance's program (numbers of rules, atoms and constraints of each kind) and of a few short probing runs of the solver (choices, conflicts, learnt constraints, backjumps).

**What the test data stands for.** Whole problem families (the instances of one generator, 75 families) are held out, 25 in each test fold, so the test data stands for a kind of problem never seen in training, as for a user with a new encoding.

**Our changes to the source.** We drop instances that no configuration solved within the time limit, and hold out whole problem families where claspfolio 2 and ASlib split instances at random. ASlib adds the cost of computing the features to the selected runtime; we leave it out, as it is the same whichever configuration is picked.

> **Use case fit: approximate (a stand-in with a known gap).** The features exist before solving, a held-out family matches a new encoding, and the score is the time the user loses with the pick, timeouts included. But instances that no configuration solved are dropped, which a user cannot know in advance.

## Curation notes

We get the data from ASlib and merge them into one file.

- Task (Andrej, 2026-11-04): runtime regression with one row per instance and configuration, as sat11_hand_algo_runtime. A selector in use learns from the full table of runs, every configuration on every training instance, timeouts included, and the user loses time mostly to timeouts (96% of the single best configuration's PAR10 comes from them). Until then the task was multiclass classification of the fastest configuration, as in the OpenML version (https://openml.org/d/41705), scored by log loss as a stand-in for PAR10; that label counted a pick 0.05 s slower as wrong as a timeout (for 62% of the instances the second-best configuration is within 1 s of the best) and no model saw a runtime or a timeout. On the 30 splits of the classification definition, always running the configuration most often fastest in training gives a PAR10 of 611 s, the best pick per instance 21 s; untuned LightGBM trained this way picks at 646 s.
- We drop all instances that no configuration solved before the 600 s timeout (all their runtimes are the censored limit, and every choice costs the same). We keep the 1,963 timeouts of the other 1,212 instances at the limit of 600 s (every finished run took at most 599.7 s): selecting the fastest configuration needs every configuration's outcome, and the limit keeps the order within an instance and is enough to compute PAR10.
- Timeouts stay at the recorded 600 s in the target (Andrej, 2026-11-06): it is the value ASlib records, and how to
  treat a censored run is left to the models; the scoring, ASlib's PAR10, charges a timeout ten times the limit.
  Counting timeouts at that charge (6,000 s) in the target moved the picks only within noise here (better with
  LightGBM and linear models, worse with a random forest and TabPFN).
- We log scale the target. The configuration's name (`algorithm`) is a categorical feature: the scenario publishes no configuration features.
- The instance id is anonymised and ships as a scoring column only: the metric picks per instance the configuration with the lowest predicted runtime. Never a feature.
- We resolve the instance ID to a problem family (`problem_family`) from its path: the instance path without the file name, for example `ASP-Comp-2011-Lparse/26-Solitaire`. A family holds different instances of one problem from one generator (here, Solitaire puzzles), and the best configuration depends on the family, which the instance features fingerprint. claspfolio 2 and ASlib split the instances at random, so their test instances come from known families; we hold out whole families instead, to predict the runtimes on a problem family not seen in training (the `definition` of the grouping).
- Families, not class folders (Andrej, 2026-11-18, blind split review, the same key as sat11_hand_algo_runtime): some folders hold one generator twice or in parts, and are merged: the 15 problems of the 2007 competition stored both under `ASP-Comp-2007-Lparse/SLparse/` and directly under `FolioSuite/` (20 file names on both sides, 11 with identical features), `HamiltonClumpy`'s five parameter folders, `RLP-150` and `RLP-200`, and the plain and verbose `searchTest` (identical programs). The 96 class folders give 75 families. Grouped on the folders (`task_id` until 2026-11-18), 19% of the test instances (4-45% per fold, 30 folds) had their generator in training. The same problem under another competition's encoding (Towers of Hanoi in 2007, 2009 and 2011; Labyrinth in 2009 and 2011; Schur numbers in 2007 and 2009) stays its own family: a new encoding is the use case.
- Metric: ASlib's PAR10 of the configuration predicted fastest per instance. ASlib adds the feature costs (`feature_costs.arff`) to the selected runtime; they are the same whichever configuration is picked, so we leave them out.
- To do: rename the dataset (it is no longer a classification task) once the BeyondArena v0.2 review page is done; its marks are stored under the current name.
- Time basis: UnseenGroup (Andrej, 2026-11-18; `Timeless` before): the use case picks a configuration for a kind
  of problem not seen before, so whole problem families are held out. Every run comes from the one experimental
  campaign of claspfolio 2 (Hoos, Lindauer and Schaub 2014) on one machine with a 600 s limit; features and
  probing runs are computed before the run, and the runtime is a property of the instance and the configuration
  on that machine. The instance collections are of earlier years, but only ASP-Comp-2007, -2009 and -2011 name
  one, so no split by time is possible; problem families are held out instead. Not tested: another machine or a
  newer clasp version.

## Group structure

One group is a problem family of the Potassco ASP benchmark set: the instances of one generator, a class folder with the folders of one generator merged (75 families); its rows are the runs of the 11 clasp configurations on its instances, with the log runtime as the target.
