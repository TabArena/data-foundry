## In brief

**Question.** Does a function of a NASA software system have a reported defect?

**Use case.** For example, a verification team decides which modules of a large C program to inspect by hand first, from static code measures that are cheap to collect (the use the source describes).

**One row.** One module (a C function) of JM1, a NASA real-time ground system that simulates missions, from the NASA Metrics Data Program (8,736 modules after removing duplicates); the period is not stated.

**Predicted.** Whether the module has one or more reported defects (22% do). Over which period the defects were reported is not stated.

**Known at prediction time.** 21 static measures of the module's code: line counts (code, comments, blank lines), McCabe measures of the complexity of its control paths, and Halstead measures from counts of operators and operands.

**What the test data stands for.** Random modules of the same program, so the test data stands for modules of this program not yet inspected.

**Our changes to the source.** We drop exact duplicate rows and every copy of a code-measure profile that appears with both labels (10,885 to 8,736 rows); 25% of the rows shared their profile with another row.

> **Use case fit: approximate (a stand-in with a known gap).** Inspecting the riskiest modules first is a real decision, but the label has no stated horizon and when the code was measured relative to the defect reports and their fixes is not stated, so the measures may describe the fixed code.

## Curation notes

- We selected this dataset as representative of a set of predictive modeling tasks of software engineering (other examples of such tasks are available on OpenML under the names mozilla4, pc1, pc2, pc3, mc1, kc1, kc2). This dataset was selected as it has the largest sample size.
- We drop duplicates. 25% of the rows share their code-metric vector with another row (669 groups, mostly trivial modules such as 173 copies of a 4-line, complexity-1 function), so a random split puts copies on both sides. We drop exact duplicate rows (1,973) and then every copy of a metric vector that appears with both labels (88 vectors, 176 rows): 10,885 -> 8,736 rows.
- The source URL is jm1.arff of the PROMISE repository, donated in 2004 by Tim Menzies from the NASA Metrics Data Program; it answers over plain http but gives 404 over https, and the Wayback Machine holds the same file. We read OpenML dataset 1053, whose ARFF is byte-identical to it (see the download description).
- The target (2026-11-01, CLEAN-25): `defects` ships its classes as words (True means defects). Binary: "Yes" is
  the event, the class that sorts second, so it is the metrics' positive class.
- Anomaly: on 893 rows (10.2%) all 16 Halstead and line-count measures are 0 while the size and complexity
  measures are not (loc 4 to 1,129, v(g) 1 to 128), so the Halstead tool gave no output for those functions.
  Kept as shipped: tested, the zeros mark no class. The flag alone scores ROC AUC 0.52 (defect share 0.30
  against 0.21, higher among large modules and lower among small ones), and gradient boosting scores the same
  with the zeros as shipped or set to missing (0.709 against 0.710, 5 folds; review of 2026-11-04).
- Time basis: Snapshot: one extraction of the static code measures of one version of JM1, joined with each
  function's defect reports (NASA Metrics Data Program; donated to PROMISE on 2 December 2004); the test
  functions are functions of the same code base at the same moment (2026-11-12, Andrej, review issue 2 A).
  When the code was measured relative to the defect reports and their fixes is not stated. The random split
  cannot test a later release of the code, nor defects that one report shares across the functions of a file
  (the data has no file or function name).
